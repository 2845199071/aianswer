# 双来源判定 & 自动翻页（v7.7）

## 一、同一道题同时存在题库和记忆库，怎么判

### 判定顺序（`QService.tick`）

```
读屏
 ├─① 自选题库（开关开 && 已导入 && 不是手动「识别」）
 │     命中且按文本定位成功 → 直接出答案，**后面的记忆库不再参与**
 │
 ├─② 记忆库（审核通过 && 无分歧）
 │     命中且按选项文本定位成功 → 0ms 出答案
 │
 └─③ AI（投票 / 路由 / 在线优先）
       答完写回记忆库
```

**自选题库永远优先。** 理由：它是用户从外部导入、可以对照原卷核对的权威数据；
记忆库是 AI 逐步攒的推断结果，可靠性低一档。

### 情况 A：答案一致，选项不一致

「选项不一致」有两种，处理完全不同：

| 选项哪里不一致 | 结果 |
|---|---|
| **顺序不同**（内容一样，排列变了） | 两个来源都按**选项文本**定位，各自算出的屏幕字母相同 → 一致，正常出答案，不提示 |
| **文字不同**（题库写「4年」，屏幕写「4 年」/「四年」） | 题库的 `findTextIndex` 阈值 0.75，轻微差异能容忍；差太多 → 题库定位失败 → **不占用结果位**，落到记忆库；记忆库也失败 → 问 AI |

也就是说：**答案一致时，谁定位成功就用谁，用户不会被打扰。**

### 情况 B：答案不一致

- **v7.7 之前**：自选题库命中即 return，记忆库压根没被读。界面上只有题库的答案，
  **完全不知道两个来源打架了**。这是设计缺口——题库导错了也不会有人发现。
- **v7.7 起**：自选题库命中时，顺手把记忆库的答案也按文本翻译成屏幕字母，
  两者一比：

| 结果 | 界面表现 | 是否自动点 |
|---|---|---|
| 一致（多选按集合比，`AB`=`BA`） | 正常出答案 | ✅ |
| 不一致 | **红框** + 第二行「记忆库给了不同答案，没敢用」+ 答案下方并排列出记忆库的选项 | ❌ |

不一致时仍以题库为准（可复核的数据优先），但**不再沉默**。用户看到红框就知道该去核对题库。

### 为什么不在这种情况下问 AI

已经有两条互相矛盾的权威数据，再拉第三个来源投票只会多一个声音，
而且每次遇到都要烧额度。此刻需要的是人看一眼题库原文，不是再算一遍。

## 二、自动翻页（学自刷题助手·固定题库版）

### 刷题助手的原实现（`FloatService` phase 状态机）

| 阶段 | 动作 | 关键细节 |
|---|---|---|
| phase 0 | 读屏 + 匹配 + 点第一个答案字母 | 每拍重新读屏，节点永远新鲜 |
| phase 1 | 逐个点剩余字母 | 失败有 `phase1Wait` 兜底重试，最多 10 拍 |
| phase 2 | 点「下一题」 | 点完 500ms 先看一眼，没翻页再轮询 4 次（每次 400ms） |
| 回到 0 | 继续下一题 | `lastQuestion` 相同则 `repeatCount++`，≥3 停 |

停止条件：找不到「下一题」/ 题干三次没变 / 页面无响应 / 读屏服务没了 / 切到别的 App。

### 本项目的实现

刷题助手是「自己驱动轮询」的常驻循环；AI答题 是「无障碍事件驱动」——
页面一变化就有 `CONTENT_CHANGED`，tick 自动跑。所以只需要补「点下一题」这一拍：

```
答完 → clickLetters 点选项 → 700ms 后 nextRun
                                    ├─ 重新读屏（旧节点已失效）
                                    ├─ 校验包名（不在答题 App 里就不点）
                                    ├─ r.next == null → 放弃
                                    └─ click → 主动 fire 一次，防止页面不产生事件
```

### 比刷题助手保守的四处

1. **只有真的点过选项才翻页**。判不准、有分歧、选项对不上时不翻，留给人看。
2. **只在本 App 内翻页**。答题途中切到微信/浏览器，它们也有「下一步」，不拦会替用户点掉别人的按钮。
3. **防连点 1200ms**。
4. **默认关闭**，开启时要二次确认（会说清「会一题接一题连答」），并且依赖「自动点击选项」。

### 设置入口

`设置 → 解题行为 → 答完自动点「下一题」`

- 默认关
- 自动点击关掉时自动置灰并说明原因
- 关闭自动点击会连带关掉它

## 三、这轮踩到的真问题：手势点击会「假成功」

### 现象

自动翻页接上之后，界面显示「记忆库 回答 · 0ms · 已自动点」，
但**选项没有高亮**，答题 App 的「对 0 · 错 0」也不动 —— 点了等于没点。

更麻烦的是日志和 Toast 都看不到（这台 ROM 把 app 的输出通道都掐了），
只能靠「关掉拟人点击 → 界面立刻正常」这个对照实验定位。

### 根因

`ScreenScan.click(svc, node, human)` 在拟人模式下**跳过 ACTION_CLICK，只发手势**：

```java
if (!human) { 遍历父链 performAction(ACTION_CLICK) }
// human: 直接 dispatchGesture
```

`dispatchGesture` 返回 true 只代表「手势投递成功」，**不代表控件收到了点击**。
在部分机型 + 部分 App 上它会被吞掉，于是出现「返回 true、界面没反应」。

### 修复

节点点击永远优先，拟人模式也不例外：

```java
// 先沿父链找 clickable 祖先，ACTION_CLICK 成功就返回
// 只有节点不可点击时才走手势（此时 human 决定按压时长与 ±3dp 偏移）
```

拟人的「手感」由调用方的随机间隔（每个字母 120~260ms、翻页前 700ms）继续提供，
不靠「跳过节点点击」来实现。

### 影响面

这个问题从 v7.1 引入拟人点击就存在，只是之前偶尔成功没被发现。
**关掉拟人点击的用户从来没受影响**（那条路一直走 ACTION_CLICK）。

## 四、验证

### JVM

| 用例 | 断言 | 结果 |
|---|---|---|
| 答案集合比较（AB=BA、AB≠A、ABD≠AB、空/null/小写） | 8 | 全 PASS |
| 双来源串起来：记忆库 CA → 屏幕 AC，与题库 AC 比对 | 2 | 全 PASS |

### 真机（REDMI Turbo 5 Max，考试 App 顺序练习 50 题）

| 验证项 | 结果 |
|---|---|
| 设置页新增开关、默认关、依赖置灰 | ✅ 灰色滑块 + 说明文案 |
| 开启二次确认 | ✅ 「开启自动翻页？」说明会连答 |
| **自动连答** | ✅ 20 秒内从第 1 题跑到**第 8 题，对 7 · 错 0** |
| 拟人模式下点击生效 | ✅ 关闭前 A 不高亮；修好后 A 绿色高亮 + 「✓ 答对了」 |
| 关闭后停止翻页 | ✅ 开关复位为灰 |

### 未覆盖

- 题库与记忆库**答案不一致**的红框提示：需要人为造一条记忆库答案与题库不同的记录，
  没在真机上构造（逻辑由 JVM 的 `sameSet` 用例覆盖）。
- 找不到「下一题」时的停止：本机考试页一直有「下一题」，没跑到。
