# 记忆库：按选项内容存答案（v7.6）

## 一、原来的问题

记忆库条目只存了题干和答案字母：

```json
{"a":"B","q":"减速机整体换油周期为每多少年?"}
```

同一道题第二次出现时，代码直接 `hit.letters = bankEntry.a` 把 `B` 抛出去。如果这次屏幕选项顺序和录制时不同，`B` 就指向了另一个选项——**题干一样、答案字母一样、结果却是错的**，而且界面上一切正常，用户没有任何办法发现。

自选题库早就按内容定位了（`SelfBankMatch`），记忆库一直没跟上，成了整个调度链里最薄弱的一环。

## 二、字段结构调整

```json
{
  "q":  "减速机整体换油周期为每多少年?",
  "a":  "B",
  "op": {"A":"2年","B":"4年","C":"6年","D":"8年"},
  "os": 0,
  "s":  "单模型 · DeepSeek V4.1-Flash",
  "c":  85, "h": 3, "t": 1762766000000,
  "l":  false, "v": true, "w": false,
  "cf": []
}
```

| 字段 | 含义 | 变化 |
|---|---|---|
| `a` | 答案字母 | 不变。**但它的语义变了**：从「屏幕上的位置」变成「录制那次的选项编号」，只在 `op` 里查表用 |
| **`op`** | **选项原文：字母 → 文本** | **新增**。命中时按它把字母翻译成内容，再在屏幕上重新定位 |
| **`os`** | **选项对不上的累计次数** | **新增**。连续 2 次 → 条目打回「待确认」 |
| `v` | 是否审核通过 | 沿用。只有 `v=true` 才允许 0ms 直出 |
| 其余 | 来源/置信/命中数/时间/锁定/错题/冲突 | 不变 |

为什么 `op` 用对象而不是数组：数组只能表达顺序，对象保留了「录制时哪个字母对应哪段文字」这个事实。命中时这两件事都要用——字母索引文本，文本再去匹配屏幕。

存储开销：4 个选项约 80~120 字节，一条记忆从 ~170 字节涨到 ~300 字节。19 条记忆多占 2KB，可忽略。

## 三、匹配逻辑

命中记忆库时，不再照抄字母，走三步：

```
记忆: a="B", op={A:2年, B:4年, C:6年, D:8年}
                  │
        ① 查表：B → "4年"          （拿到的是内容，不是位置）
                  │
        ② 在当前屏幕的选项文本里找 "4年"
           Matcher.findTextIndex("4年", ["8年","4年","2年","6年"], 0.75, 0)
                  │
        ③ 命中下标 1 → 字母 B'     （B' 是这次屏幕上真正该点的字母）
```

`findTextIndex` 用的是刷题助手验证过的归一化匹配：去题号/标点/空白后再比，
并用 `symSig` 校验正负号方向（`+15%` 和 `-15%` 归一后完全相同，不校验就会点反）。

### 三种结果

| 情况 | 判定 | 输出 | 置信 | 自动点击 |
|---|---|---|---|---|
| 文本全部定位成功，字母和记忆一致 | `mapped=true, orderChanged=false` | 记忆字母 | 1.00 | ✅ |
| 文本全部定位成功，字母变了 | `mapped=true, orderChanged=true` | **屏幕字母** | 0.95 | ✅ |
| 记忆里没有 `op`（旧数据） | `noOpts=true` | 走 AI 复核，不当命中 | — | — |
| 有 `op` 但屏幕对不上 | `mapped=false` | 走 AI 复核，记忆答案作对照 | 0.40 | ❌ |

多选题按集合比较：记忆 `AB` 映射出 `BA` 不算顺序变化（点哪几个才是关键），
避免「顺序变了」的提示在每道多选题上都刷一遍。

**关键设计：命中后不改写 `a`。** 记忆里始终保留录制时的字母，每次都从 `op` 重新翻译。
如果改成「用这次的屏幕字母覆盖 `a`」，下次顺序再变就又要重新猜一遍，而且把一次偶然的
位置关系固化成了事实。

## 四、有效性校验

四道关，从写入到命中层层收紧：

### 1. 写入关：必须带选项

`bankAuto` 只在拿到 ≥2 个屏幕选项时才写 `op`；模型答案与库内一致时也会刷新
`op`（以最新一次屏幕为准），旧记录的空白 `op` 就在这一步被补齐。

### 2. 命中关：文本必须对得上

- 每个答案字母都要在 `op` 里查到文本 —— 查不到直接判失败（数据不完整）
- 文本要在屏幕上找到相似度 ≥0.75 的选项 —— 找不到判失败（题目改版或识别不全）
- 多个答案不能落到同一个选项 —— 撞车判失败（异常数据）

任何一条不满足 → `mapped=false`，**不占用结果位**，继续走 AI，记忆里的答案作为
「对照」显示在答案下面，让用户知道分歧在哪。

### 3. 累计关：`optStale` 计数

- 定位成功 → `os` 清零
- 定位失败 → `os++`，**连续 2 次**才把 `v` 置 false，打回「待确认」

单次失败不惩罚：屏幕偶尔只渲染出一部分选项（滚动、懒加载），一次对不上不代表记忆坏了。
连续两次说明这条记忆的选项内容大概率过时了，退回「下次重新问一遍模型」的状态。

### 4. 审核关：`v`（沿用 v7.4 的机制）

- 新建条目 `v=false`（待确认）
- 模型第二次独立作答一致 → `v=true`
- 出现分歧 → 打回 `v=false`
- 用户手改答案 / 采纳某个候选 / 点「确认可用」→ `v=true`

只有 `v=true` **且** 本次 `mapped=true` 才允许 0ms 直出。

### 旧数据怎么办

v7.6 之前存的条目没有 `op`。它们现在的行为：

1. 命中时判 `noOpts`，**不再直接照抄字母**（那正是本次要消灭的风险）
2. 转去问一次 AI，AI 答完 `bankAuto` 顺带把 `op` 补齐
3. 答案一致 → `v=true`，从此按内容定位

代价是 19 条旧记忆各多问一次，一次性。收益是它们从此也能抗住选项乱序。
题库详情页会如实提示「这条记忆是旧版本存的，没有选项内容」。

## 五、验证

### JVM（不依赖真机）

| 用例 | 断言 | 结果 |
|---|---|---|
| `AnsResolver` 顺序未变 / 打乱 / 全乱序 / 多选换序 | 15 | 全 PASS |
| 正负号相反的选项不混淆、屏幕选项不全、缺字母、选项撞车、多出选项 | 含在上述 15 项 | 全 PASS |
| `Record` 的 `op`/`os` 落盘与读回、旧纯字母数据兼容、无选项条目省空间 | 10 | 全 PASS |

其中关键的三个：

```
顺序未变：B → B          ├ mapped=true  conf=1.00
顺序打乱：B(220V)→A 位   ├ letters=A    conf=0.95  moved=true
全乱序：  220V 在第 3 位 ├ letters=C    conf=0.95
```

### 真机（REDMI Turbo 5 Max）

- **旧记录补全**：`记忆库命中 A → A mapped=false`（noOpts）→ 走 AI 复核 → 题库详情页出现完整的 4 行选项
- **按内容命中**：`记忆库命中 A → A mapped=true moved=false` → 悬浮窗 `记忆库 回答（已确认）· 0ms · 已自动点`
- 详情页能看到 App 到底存了什么，不再是黑盒

### 未覆盖

真机上没能制造选项乱序（考试 App 的选项顺序固定），乱序场景只有 JVM 覆盖。
如果要真机验证，最省事的办法是临时改 `AnsResolver.CONF_MOVED` 分支的日志级别，
在模拟器上跑一份选项顺序不同的同题题库。
