## 0. 一条题目从头到尾

```
无障碍事件（CONTENT_CHANGED / WINDOW_CHANGED）
        │  防抖 + 1200ms 静默期 + 同题判重
        ▼
ScreenScan.scan()   ── 根节点 → 可见文字节点 → 按屏幕坐标排序
        │
Layout.parse()      ── 题干 / 选项 / 「下一题」/ 剥离题号·分值·倒计时
        ▼
QService.tick()     ── 三层短路判定
   ├─① SelfBank.find()          自选题库，按选项文本定位
   ├─② Record + AnsResolver     记忆库，按选项文本重定位
   └─③ AnswerEngine.answerAsync 投票 > 题型路由 > 在线/本地
        │
        ▼
onAnswer()  ── 置信度门槛 → Overlay 显示 → clickLetters() → nextRun()
                └─ Record.bankAuto() 写回记忆库（五级仲裁）
```

**关键设计：上层命中即 `return`。** 题库命中时 `AnswerEngine` 根本不会被调用，所以路由、投票与题库不会互相打架；投票只在 AI 那一层里发生。

## 1. 读屏：怎么把一棵无障碍树变成「题干 + 选项」

### 1.1 选对窗口（`ScreenScan.pickRoot`）

不能直接用 `getRootInActiveWindow()`：在部分机型上，我们自己的 `TYPE_APPLICATION_OVERLAY` 悬浮窗会被算成活动窗口，那样读到的是**自己面板上的文字**，题干自然永远对不上题库。

实现改为遍历 `getWindows()`：

1. 只取 `TYPE_APPLICATION`（跳过输入法、状态栏、悬浮层）；
2. 包名等于自己 → 跳过；
3. 优先 `isActive()` 的那个，没有就取任意符合条件的应用窗口；
4. 兜底路径若发现根节点是自己，宁可返回空，也不把面板文字当题目读。

### 1.2 收集与排序（`collect` / `sortByPosition`）

- 深度上限 40；`isVisibleToUser()` 为 false 的节点**连同整棵子树跳过**（H5 页面隐藏节点常占一大半，这一刀是主要提速点）。
- 文字取 `getText()`，为空则取 `contentDescription()`，换行压成空格。
- 每个文字节点同时记录 `{top, left}` 屏幕坐标。
- **按坐标重排**：H5 / WebView 的无障碍节点顺序跟随 DOM，不等于视觉上的从上到下。直接按遍历顺序「从选项往前倒推题干」会把页面标题当成题干（实测墨学云踩过）。排序规则：`top` 差 >12px 视为不同行按上边界排，同一行按 `left` 排。原生 App 本来顺序就对，排序无副作用。

### 1.3 版面解析（`Layout`，纯 Java 可单测）

| 规则 | 做法 |
|---|---|
| 选项行 | `OPT_FULL` 吃 `A. 内容` / `A、内容` / `（A）内容` / `A 内容`；`OPT_BARE` 处理字母单独成节点、内容在下一个节点的情况 |
| 题干 | 找到第一个选项行，往前取文字；有坐标时按坐标取，没有时按序遍历 |
| 噪声 | `isJunk()` 挡纯题号、进度、`（1分）`、`27:38`、「剩余 12:30」、题型标签等 |
| 动态前缀 | `stripDynamic()` 循环剥离「第13题」「7/50」「（单选题）」「单选题（第1/共10题）」，再剥首尾时间片段 |
| 分值 | `stripScore()` 去掉「（1分）」——否则归一化后「1分」会粘进题干变成「…红表笔插入孔1分」 |
| 下一题 | `NEXT_WORDS`（下一题/下一页/继续答题/下一步…）收集候选，优先取 `isClickable` 的；`STOP_WORDS`（交卷/提交试卷…）绝不点 |

**为什么必须剥倒计时**：答题页每秒刷新 `27:38`，若混进题干，同一道题每拍都会算出不同的 `sig`，上层判重失效、模型被反复调用。`isJunk` 里那条规则**不能带 `.*$`**（曾把整道真题判成噪声，导致题干落到页面标题上，这里限制长度 ≤12 且只挡纯题号形式）。

题干节点坐标还会反查一次（用题干前 8 个字匹配），供悬浮窗避让 —— 只避选项的话，悬浮窗一高就会压住题目第 1 行。

## 2. 什么时候重新算（`QService.tick`）

一层层拦，能不重算就不重算：

1. 在线和本地**都不可用** → 显示「未就绪」直接返回。
2. 扫描结果 `options.size() < 2` → 返回（多半不是答题页）。
3. `skipPkg(pkg)` → 跳过自身及排除名单里的 App。
4. 题干 `< 4` 字 → 返回。
5. `signature(题干 + 选项)` 与上次相同 → 返回（同一道题，答案已在屏幕上）。
6. 距上次出答案 `< 1200ms` → 挂 600ms 后再试（倒计时、进度条每秒都在制造 `CONTENT_CHANGED`，不拦会出现「刚显示答案立刻又思考中」）。
7. 通过后才更新 `lastSig`、记录 `lastScreenOpts`（字母 → 选项原文）、`answerPkg`、`hurryMode`，并**先避让悬浮窗再显示「思考中…」**。

## 3. 三层判定链

### ① 自选题库（`SelfBank` / `SelfBankMatch` / `Importer`）

前置：`!verify`（不是手动「识别」） && 「先查自选题库」开 && 确实导入过。

- 匹配复用「刷题助手·固定题库版」的 `Matcher.norm / symSig / matchBest / findTextIndex`：归一化后比题干和选项文本，`symSig` 校验正负号方向（`+15%` 和 `-15%` 归一化后一样，不校验会点反）。
- 三处加固：
  - `MIN_STEM = 0.45`：题干相似度低于 0.45 直接判未命中，**选项再像也不认**（同一份卷子相邻题常共用一批选项，只靠选项分会误命中）。
  - 题干 ≥0.95 时豁免选项分（`12V` vs `十二伏特` 这类写法差异不该把 100% 相同的题干拒掉）。
  - 多份题库合并成一个数组检索；删掉某份后自动重建。
- 题库答案存的是**选项文本**，命中后用 `findTextIndex(文本, 屏幕选项列表, 0.75, 0)` 定位到本次屏幕的字母 —— 所以选项乱序不会点错。
- **命中但定位失败 → 不占结果位**，继续往下走；题库答案只作为「对照」显示在答案下面。AI 也失败时才退回题库答案，且置信压到 0.40（低于阈值，不自动点击）。
- 自选题库命中**不写本机记忆库**：否则会污染「AI 记住 N 题」的统计，两套答案打架时也分不清来源。
- 同时会顺手把记忆库答案也按文本翻译成屏幕字母，`sameSet()` 比一次：不一致 → 红框 + 列出两方答案 + 置信 0.45 → **不自动点**。有两条互相矛盾的权威数据时，再拉第三个模型投票只会多一个声音，此刻需要人核对题库原文。

**导入**（`Importer` + `XlsxReader` / `DocxReader` / `TextParser`）：xlsx/xlsm 直接读 OOXML，csv/tsv/txt/docx 按「题号 + 选项行 + 答案行」切题，json 直接吃。会在**前 30 行**自动找表头跳过「导入须知」；答案支持 `ABCD` 连写、`A,B`、正确/错误、`√/×` 和选项原文；老 GBK txt 会检测替换字符后重解码。存储为 App 私有 `files/selfbanks/<id>.json` + `.meta.json`，另有 `SharedPreferences("selfbank_index")` 索引 —— 索引的用途是**发现文件丢失**：清理工具删掉文件时界面显示「文件丢失，请重新导入」，而不是装作没导入过。

### ② 记忆库（`Record` + `AnsResolver`）

条目 JSON（v7.6 起）：

```json
{
  "q": "减速机整体换油周期为每多少年?",
  "a": "B",
  "op": {"A":"2年","B":"4年","C":"6年","D":"8年"},
  "os": 0,
  "s": "单模型 · DeepSeek V4.1-Flash",
  "c": 85, "h": 3, "t": 1762766000000,
  "l": false, "v": true, "w": false,
  "cf": []
}
```

| 字段 | 含义 |
|---|---|
| `a` | 答案字母，**语义是「录制那次的选项编号」**，只在 `op` 里查表用，不再是屏幕位置 |
| `op` | 选项原文映射（字母 → 文本） |
| `os` | 选项对不上的**连续**次数 |
| `v` / `l` / `w` | 审核通过 / 用户手改锁定 / 错题 |
| `cf` | 冲突候选列表 |
| `s/c/h/t` | 来源 / 置信 / 命中数 / 时间戳 |

**命中三步**：`a="B"` → 查 `op` 得「4年」 → 在当前屏幕选项文本里找相似度 ≥`MIN_SIM=0.75` 的下标 → 得到这次该点的字母。`findTextIndex` 先归一化（去题号/标点/空白）再比，并用 `symSig` 校验正负号。

| 结果 | 置信（`AnsResolver` 常量） | 行为 |
|---|---|---|
| 全部定位成功、字母未变 | `CONF_SAME = 1.00` | 0ms 直出 |
| 全部定位成功、字母变了 | `CONF_MOVED = 0.95` | 用**屏幕字母**直出，标注「选项顺序变了」 |
| 旧记录没有 `op` | `CONF_NO_OPTS = 0.55` | `noOpts=true`，**不照抄字母**，转 AI 复核并顺带补齐 `op` |
| 有 `op` 但对不上 | `CONF_MISS = 0.40` | `mapped=false`，不占结果位，走 AI，记忆答案作对照 |

失败还分原因：记忆里缺某个字母的文本 / 该文本在屏幕上找不到 / 两个答案定位到同一个选项（撞车）。多选题按**集合**比较（`sameSet`，`AB` = `BA`），避免每道多选都刷「顺序变了」。

**命中后不改写 `a`**：记忆里始终保留录制时的字母，每次都从 `op` 重新翻译。若用本次屏幕字母覆盖 `a`，就把一次偶然的位置关系固化成了事实。

**四道有效性校验**：

1. 写入关：`bankAuto` 只在拿到 ≥2 个屏幕选项时才写 `op`；模型答案与库内一致时也会刷新 `op`（以最新屏幕为准），旧记录的空 `op` 就在这里补齐。
2. 命中关：每个答案字母都要能查到文本、文本要在屏幕上找到 ≥0.75 的匹配、多个答案不能撞到同一选项。任何一条不满足 → `mapped=false`。
3. 累计关：定位成功 `os` 清零；失败 `os++`，**连续 2 次**才把 `v` 置 false 打回待确认。单次失败不惩罚（屏幕可能只渲染出部分选项）。
4. 审核关：新建 `v=false`；模型第二次独立作答一致 / 用户手改 / 采纳候选 / 点「确认可用」 → `v=true`；出现分歧 → 打回 `false`。**只有 `v=true` 且 `mapped=true` 才允许 0ms 直出**。

**冲突五级仲裁（`bankAuto`）**：

| 优先级 | 情况 | 行为 |
|---|---|---|
| 1 | `locked=true`（用户手改过） | 直接出题库答案，模型持异只在角标提示，**永不覆盖** |
| 2 | 命中且与本次模型一致 | `hits+1` 正常出 |
| 3 | 命中但模型不同 | **不覆盖**，显示高置信一方，模型答案写进 `cf[]`，标「有分歧」 |
| 4 | 冲突累计 ≥2 条、来源不同、答案一致 | 悬浮窗提示「是否更新题库？」由用户点，**绝不自动改写** |
| 5 | 库里没这题 | 写入首次答案，`locked=false`, `hits=1` |

多选必须**字母集合完全相等**才算一致，`ABD` 与 `AB` 视为不同 —— 漏选/多选在考试里都是错，自动合并会掩盖真实分歧。

### ③ AI 调度（`AnswerEngine`）

单个 `newSingleThreadExecutor` 串行推理，结果 `post` 回主线程；本地 llama 只有一个实例，本来也不能并发。

优先级：**投票 > 题型路由 > 在线优先/本地优先**。

**题型路由（`Router.decide`，纯规则，宁可大不小）**：

| 命中任一 → 在线大模型 | 判定 |
|---|---|
| 数学计算 | `= + × ÷ √ ∑ %` 等符号、小数，或「计算/求解/面积/概率/导数…」 |
| 文言文 | 「之乎者也焉曰」「加点词」「通假」「出自《」「子曰」等 |
| 长题干 | 题干 > 120 字 |
| 多选多项 | 多选且选项 ≥5 |
| 专业条文 | 「法条第/应当/不得/临床/剂量/税率/增值税…」 |
| 英文长句 | 多个长英文单词且题干 > 60 字 |
| 题干为空 | 保守走在线 |

都不命中且题干 ≤40 字、选项 ≤18 字、单选 → 本地小模型；其余中等长度题兜底也走本地省额度。路由理由（`reason`）直接显示在悬浮窗来源行，如「路由：数学计算 → 在线」。

**降级链**：首选在线失败/熔断 → 本地旗舰（已下载）→ 本地 1.5B → 报错；首选本地未加载 → 在线 → 报错。只配一条通道时路由开关虽亮但不生效，设置页会橙色提示。

**多模型投票**：前置 `cloudReadyCount >= 2`（`Prefs.cloudReady` 按 provider 统计，自定义厂商还要 Base + 模型名），否则开关置灰。参与厂商取「免费优先」排序后的前 3 家（`Prefs.cloudReadyList`），串行调用（避免并发限流）。总预算 `VOTE_BUDGET_MS = 9000`；检测到倒计时进入抢答模式，压到 `VOTE_BUDGET_HURRY_MS = 4500`。计票多数胜，平票取免费优先 + 置信高；全票一致置信 0.95，2:1 为 0.8，三方全不同标红且**不自动点击**。`askCloudAny` 会按健康度换下一家，不把时间耗在已熔断的厂商上。投票与「复核」互斥（否则一次答题跑 3~4 次调用，免费额度会烧穿）。

**熔断与健康度（`CloudSolver`）**：`failStreak` / `cooldownUntil` 都是**按 `provider.id` 隔离**的 Map（早期版本是全局静态且任何成功都 reset，导致投票时只剩 1 家）。瞬时错误连续 2 次 → 冷却 90 秒；欠费/额度用尽这类永久错误 → 直接冷却 10 分钟。`orderByHealth` 按成功率降序、同分按平均耗时升序排，`noteOk/noteFail` 记录统计供设置页展示。

**在线请求**：OpenAI 兼容 `/chat/completions`，`max_tokens` 单选 24 / 多选 48；思考模型默认开 thinking 会先输出思考过程吃光 token，所以请求里显式关掉并在返回后按 40 字硬截一次。

**本地推理（`Llama` + `PromptBuilder`）**：

- so 按 `ggml-base → ggml → ggml-cpu → llama → aiq` 顺序 `System.loadLibrary`，顺序颠倒会加载失败。
- `PromptBuilder.build` 用 Qwen2.5 ChatML 模板，结尾停在 `<|im_start|>assistant\n答案：`。
- **单选不生成**：一次 prefill 后直接读 A/B/C/D 四个 token 在末位的 logits → softmax → argmax（`nativeScore`）。比逐 token 解码快 3~5 倍，也不会出现「答案是A，因为……」需要二次解析。
- 多选走 `nativeGen` 短生成，准确率低于单选。
- `ModelManager` 下载 GGUF 用 HTTP `Range` 续传，完整性用**精确字节数**校验（`len` 落在 `bytes` 的 97%~103%），`MIN_PLAUSIBLE = 200MB` 防止把错误页存成模型。清单在 `assets/models.json`，`ModelMarket` 支持下载后 `unload → load` 热插拔，每项标注适用题型/体积/耗时/模板格式。

**简洁解析**：默认关。题库自带解析直接显示（不花调用）；AI 出的答案才异步发起第二次推理，`PromptBuilder.buildExplain` 结尾停在「依据：」，在线 `max_tokens=48`、本地 24，返回按 30 字截断。悬浮窗最多 2 行，点开弹窗最多 5 行可滚动，**不落库**（落库会让题库体积翻 5 倍以上）。答案先出，解析异步补上，不阻塞。

## 4. 点击、翻页与悬浮窗

### 4.1 点击（`ScreenScan.click`）

**节点点击永远优先，拟人模式也不例外。** 沿父链最多 6 层找 `isClickable` 的祖先执行 `ACTION_CLICK`；只有整条链都不可点时才用 `dispatchGesture` 点节点中心。

这条是踩坑改的：早期「拟人」跳过 `ACTION_CLICK` 只发手势，而 `dispatchGesture` 返回 true **只代表手势投递成功，不代表控件收到了点击**。在部分机型/App 上被吞掉，出现「界面显示已自动点、选项却没高亮」的假成功。现在 `human` 只影响手势兜底那条路：落点偏 ±3dp、按压 90~180ms；拟人的间隔感由调用方的随机延迟（每个字母 120~260ms）提供。

点击期间 `Overlay.setPassThrough(true)` 给窗口加 `FLAG_NOT_TOUCHABLE`，防止悬浮窗吃掉落在它上面的手势，点完恢复。

### 4.2 自动翻页（`nextRun`，默认关）

刷题助手是「自己驱动轮询」的常驻状态机（phase 0 读屏 → phase 1 点剩余字母 → phase 2 点下一题）；AI答题是**无障碍事件驱动**，页面一变就有 `CONTENT_CHANGED`，所以只需补「点下一题」这一拍：

```
clickLetters 点完选项 → 700ms 后 nextRun
   → 重新读屏（旧节点已失效）
   → 校验包名（不在答题 App 里就不点）
   → r.next == null → 放弃
   → click → 主动 fire 一次，防止页面不产生事件
```

四道保护：只有真的点过选项才翻、只在本 App 内翻（微信/浏览器也有「下一步」，不拦会替用户点掉别人的按钮）、防连点 1200ms、找不到「下一题」或题干连续 3 次不变就停。开启需二次确认，且依赖「自动点击选项」（关掉自动点击会连带关掉它）。

### 4.3 倒计时（`TimerDetect`，纯 Java 可单测）

区分「剩余 12:30」（倒计时，触发 `hurryMode`）和「已用 28:39 / 用时 03:20」（正计时，**不触发**）。抢答模式会缩短投票预算、少问几家。

### 4.4 悬浮窗（`Overlay`）

`WindowManager` 悬浮层；`setLevel(0/1/2)` 把告警画在**外框**上（正常 / 黄色分歧 / 红色冲突），不占用答案区。`tvWhy` 限 1 行、210dp 宽、末尾省略；点它弹 `showWhyDialog` 最多 5 行可滚动。`avoid(int[] rects)` 在**思考中之前**就把窗口挪到不挡题干/选项的位置。`setPassThrough` 如上。来源行规则：谁回答的写清楚，投票一致或路由正常时不啰嗦，有分歧才展开。

## 5. 数据、隐私与边界

| 项 | 位置 / 说明 |
|---|---|
| 设置与 Key | `SharedPreferences("aiq")`，本机，不上传；在线调用次数也只在本机计数 |
| 记忆库 | App 私有目录，`bank.<md5(sig)> = JSON`；读到旧的纯字符串值会自动迁移，不清库 |
| 自选题库 | `files/selfbanks/*.json` + `SharedPreferences("selfbank_index")` 索引 |
| 导出 | `下载/AI答题/`（MediaStore），导入用 SAF 文件选择器，**不需要存储权限** |
| GGUF 模型 | App 私有目录，不进 APK，可单独删除 |
| 网络 | 仅在线推理、模型下载；本地模式全程离线；无后端、无账号、无埋点 |

**边界**：只支持 arm64（x86 装不上）；图片题抓不到（无障碍树里图片没有文字，要支持得改截图 + 多模态）；本地多选准确率低于单选；智谱免费档约 1 次/秒，切题过快会 429，此时自动回退本地。

## 6. 设计取舍 FAQ

**为什么自选题库排在记忆库前面？** 前者是用户导入、可对照原卷复核的权威数据；后者是模型自己攒的推断结果，可靠性低一档。设置项只控制「查不查」，不改变顺序。

**为什么题库命中不叫 AI，也不自动改写答案？** 省额度只是一方面；更重要的是模型偶尔会错，让一次随机输出覆盖人工核过的题库是不可逆的。分歧只记录、只提示，最終决定权在人。

**为什么记忆库要存完整选项文本？** 只存字母时，同一道题选项一乱序，`B` 就指向另一个选项 —— 题干一样、字母一样、结果却错了，而且界面上一切正常，用户无从发现。按内容定位是唯一能防住这件事的办法。多存 4 个选项约 80~120 字节/条，可忽略。

**为什么投票和复核互斥？** 复核已是「两路对拍」，投票是「多路对拍」，叠加会变成 3~4 次调用。

**为什么不在题库/记忆库答案打架时再投一次票？** 已有两条互相矛盾的权威数据，再拉第三个来源只多一个声音，还每次都烧额度。此刻需要人看一眼题库原文。

**为什么解析不落库？** 题库体积会翻 5 倍以上，而解析只在当下有用。

**和刷题助手的关系？** 复用了 `Layout` / `Matcher`（`norm` / `symSig` / `matchBest` / `findTextIndex` / `buildVariants`）以及自动选择题、点「下一题」的状态机思路；区别是刷题助手面向固定卷子、常驻轮询，AI答题面向任意页面、事件驱动，所以加了 `MIN_STEM` 下限、强题干豁免、多库合并检索、包名校验、题库与记忆库双来源比对这些保护。

## 7. 可单测的部分

`Router / AnsResolver / TimerDetect / Matcher / SelfBankMatch / MissLog / Layout / Importer / TextParser / XlsxReader / DocxReader / Record` 都是不依赖 Android 的纯 Java，可直接在 JVM 上跑断言（历史累计 60+ 项全 PASS）。改这些逻辑时**先过单测再上真机**，比靠界面点快得多。
